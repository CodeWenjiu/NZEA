# 研究计划：延迟校准 → 对标 → 创新

Status: **草案（2026-10-30）**；2026-11-01 更新：A1–A3 已完成（交付见 `latency-calibration.md`），
A4 待决策；C1 被"合成流没有外设窗口"阻塞。三个开放问题（§5）未定之前，B1–B2 可准备，C2–D1 阻塞。

## 0. 一句话

这个研究要做的是：**先让仿真里的延迟数字有出处且可复现，再用真板/真机数据交叉验证，然后在可信平台上与现有方案比速度/功耗/面积，最后做功能扩展与 CPU 设计迭代。**

顺序不可颠倒——数字不可信时，"比较"和"创新"都无处落脚。

## 1. 四条主线

| # | 主线 | 交付物 | 阻塞关系 |
|---|---|---|---|
| A | **延迟校准** | 每个延迟参数带出处；两层模型的语义分清 | 无（可立即开始） |
| B | **调研与对标** | 相关工作差异表 + baseline（速度/功耗/面积/集成度，含 CPU 与加速器） | 需 A 的自有数字 |
| C | **上板验证** | FPGA 真实运行数据 → 回填 A；FPGA→PC 数据通路 | 需 A 的埋点与 C1 |
| D | **创新** | feature 扩展 + CPU 设计取舍的量化对比 | 需 A–C |

## 2. 任务

### A 延迟校准

**A1 — 建立"延迟参数出处表"。** ✅ 完成（2026-11-01）
交付：`latency-calibration.md` §2。结论：三个 `DeviceTimings` 表与 CLINT/finisher 两个无表端口全部只影响仿真（消费点仅
`HasDpiBus.answerBus`），没有一个描述已建成的硬件；机械臂帧的两个字段有外部出处（I2C 400 kbit/s）
与推导（20 bit 帧格式）；DDR3 的 15 ns（CL 6 × 2.5 ns）是目前唯一可上板对照的量。

**A2 — 澄清"双重校准"的两层语义，并防止串味。** ✅ 完成（2026-11-01）
交付：`latency-calibration.md` §1。同一波形上：83 次访问中 66 次 ≤8 拍（线）、17 次**恰 1250** 拍
（帧），9–1249 为空档；驻留内层 83 次全部 ≤8 拍——帧把线的延迟吞在里面，不相加。

**A3 — 总线敏感度扫描（决定研究该主张什么）。** ✅ 完成（2026-11-01）
交付：`latency-calibration.md` §3。三个配置（20b/400k、56b/400k、20b/100k）实测 `busy = frames ×
帧长` 误差 0%，且 `cycle = C0 + busy` 误差 <0.3%——帧时间 1:1 在关键路径上。拐点已修正为
`B/(C0+B)`：要占到 10% 需 241 bit/帧（或 ≈33 kHz），占 50% 需 2,163 bit（或 ≈3.7 kHz）。

**A4 — `timeHz` 与软件假定的不一致（阻塞上板）。** ⏸ 待决策（证据已齐）
交付：`latency-calibration.md` §4。仿真不可观测（桥接流下 mtime 是死代码），只有上板暴露；三个选项
与代价已列，推荐 `timeHz = 10 MHz` + 仿真 50 MHz，但会动基线。

### B 调研与对标

**B1 — 相关工作差异表（防撞车）。**
做法：按"总线/片外延迟建模""机器人控制 SoC""RTL 性能建模与校准"三类各列 3–5 篇，每篇一行：方法、评价指标、是否用真实器件校准、与本工作的差异。
验收：表内每篇都能回答"我们与它的差异是否足以构成创新点"；若某篇已覆盖本工作全部主张，写进 §5 作为方向调整建议。

**B2 — baseline 定义（速度/功耗/面积/集成度）。** 🚧 初版（2026-11-01，仅 C2000）
交付：`baseline.md`。已从 `doc/tms320f28p650dk.pdf` 填出速度（200 MHz、400/600 MIPS、FPU64/TMU）、
功耗（由 §6.5.1/§6.5.2 电流与 1.2/3.3 V 推导，单核 ≈0.30 W / 双核 ≈0.40 W）、面积（仅封装 81 mm²，
裸片与工艺 N/A）与集成度（2×I2C 400k、4×SPI 50M、2×6ch DMA、6×CLB）。缺口：只有一家家族、我们的功耗/
面积为零、频率不可直接比（只能比每 tick 时间）。

### C 上板

**C1 — 用 ILA 测一次真实的"请求→应答→下一次请求"。** ⛔ 阻塞：板级没有外设窗口
位置：板级流程见 `.agents/skills/fpga-flow/SKILL.md`。
阻塞原因（2026-11-01 查证）：`nzea_device/src/PlatformDevices.scala` 的 `RtlFlow.Yosys` 清单只有
`ram`/`uart16550`/`finisher`/`clint`，没有 `peripheral`——arm/scan/motion 在板上不存在，`peripheral`
端口无从抓取。要开始 C1，先定"在板上建一条真实外设总线"（属 D1 的 DMA/批量候选）。
触发条件：合成流出现外设窗口后。

**C2 — FPGA→PC 数据通路 + 真实机械臂数据校准。**
做法：板卡把设备访问时间戳/计数经 UART 或 DDR 缓冲送到 PC，与 PC 侧的机械臂时序对齐。
验收：一次连续运行中，PC 侧记录与板卡计数的帧数一致（±1 帧），并给出"真实关节总线一次访问耗时"的实测区间。
触发条件：C1 完成后开始；若 C1 显示模型形状不符，先修模型再谈 C2。

## 4. 关键判断（会改变计划的两个事实）

**4.1 现有配置下总线不是瓶颈，校准的边际收益取决于主张。**
每 tick 计算 1,364,000 拍 vs 总线 12,500 拍 ≈ **109 : 1**；且帧时间 1:1 落在关键路径上（A3 实测），
所以占比应按 `B/(C0+B)` 算，`C0 = 1,351,500` 拍/tick：

| 目标占比 | 每 tick 需 `B` | 每帧拍数 | 对应 `bitsPerFrame`（400 kbit/s） | 对应 `bitHz`（20 bit/帧） |
|---|---:|---:|---:|---:|
| 10% | 150,167 | 15,017 | 241 | ≈ 33.3 kHz |
| 50% | 1,351,500 | 135,150 | 2,163 | ≈ 3.7 kHz |

即：要么线速再慢一个数量级，要么每帧位数多一个数量级，总线才会成为一等项。**所以论文若主张"总线建模重要"，必须选一个总线占比显著的场景（更慢的线 / 更多设备 / 无 DMA 的阻塞访问）；若主张"计算瓶颈、该做加速器"，则校准只需证明总线不是瓶颈。** 两种主张对校准精度的要求差一个量级。

**4.2 上板数字不能由仿真缩放得到。**
板卡构建的 cache 是关掉的（`nzea_fpga/src/Top.scala:108-109`，`icache = None`/`dcache = None`），时钟 100 MHz（`nzea_fpga/src/logic/BootDdr.scala:82`）。计算周期不会随频率缩小，而缺 cache 会显著增大——所以板上的"计算:总线"必须重测，不能按频率比例推算。

## 5. 开放问题（未定，不写决定）

1. **"防撞车"还是"防被复现"**：讨论中的"防止复现"指"避免与已有工作重合"（则产出 B1 差异表），还是"防止他人复现我们的平台"（则要写可复现性说明）？
2. **"双重校准"**：指两层延迟（线 + 帧驻留，§A2），还是"仿真校准 + 真机校准"两条路径？两者都成立时，A2 的对照页需要同时覆盖两个维度。
3. **feature 题目**：D1 的四个候选中选哪个？这决定 B2 的 baseline 选型（例如选"硬件三角函数/浮点"就该对标 CLA/TMU；选"DMA/批量"就该对标 2×6ch DMA；选"可编程逻辑"就该对标 CLB）。
4. **baseline 家族**：C2000 是否作为主对标？若主对标是 RISC-V 应用处理器（如带向量扩展的核），B2 全表需重做。
5. **`timeHz` 选项**：取 `latency-calibration.md` §4 的哪个（1 = 平台自洽但动基线；2 = 不动基线、软件差 2×；3 = 现状、板卡差 10×）。
6. **帧位数口径**：20（单字节帧）还是 56/66（32 位寄存器访问）——后者把总线上限从 12,500 提到 ~36,000 拍/tick。
