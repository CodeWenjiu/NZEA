# Lab 2.2 报告：缓存配置与负载敏感性

## 1. 实验环境

- gem5 v25.0（`ghcr.io/gem5/ubuntu-24.04_all-dependencies:v25-0`），X86 ISA，SE 模式
- CPU：`X86O3CPU`
- 内存：`DDR3_1600_8x8`
- L1I：32 KiB / 2 路；L1D：64 KiB / 2 路
- 默认配置：1 GHz，发射宽度 8，L2 256 KiB / 8 路
- 频率只改 CPU 时钟域（`system.cpu.clk_domain`），系统与 DRAM 时钟保持 1 GHz

## 2. 基准程序

gem5 v25 源码树只带 `hello`、`m5-exit`、`threads`，因此按讲义允许的方式自编微基准。三个程序分别覆盖「无访存」「顺序访存」「随机访存」：

| 基准 | 工作集 | 访存模式 | 控制流 | 规模 | 选择原因 |
|---|---|---|---|---|---|
| `bench_compute` | 0 | 无 | 规则 | 500,000 次迭代 | 纯计算，8 条独立累加链，用来观察发射宽度和频率 |
| `bench_seq` | 8 MiB | 顺序读 + 顺序写 | 规则 | 1,048,576 个 `uint64_t` | 空间局部性好、无复用，用来观察容量和流式访问 |
| `bench_rand` | 4 MiB | 随机指针追逐 | 洗牌循环数据相关 | 524,288 个元素 | 每次 load 依赖上一次，延迟不可重叠，用来观察容量和局部性 |

编译：`gcc -O2 -o bench_* bench_*.c`。

`bench_seq` 先写一遍数组再读一遍；`bench_rand` 先用 Fisher–Yates 生成随机置换，再沿置换做指针追逐，因此每次访问都是 L1 缺失，且无法流水化。

## 5. 分析

### 5.1 发射宽度

`compute` 从 8 宽降到 2 宽后 `simSeconds` 从 3.181 ms 涨到 7.719 ms（**+143%**），IPC 从 4.275 掉到 1.762，几乎是按宽度比例缩放。它没有访存，指令级并行足够填满 8 个发射槽，所以宽度直接决定吞吐。

`seq`（+0.9%）和 `rand`（+0.3%）几乎不受宽度影响。两者的瓶颈是访存延迟而不是发射能力：`seq` 的 IPC 只有 0.42，`rand` 只有 0.11，流水线大部分时间在等 L1 缺失，加宽也填不满。

### 5.2 CPU 频率

`compute` 在 4 GHz 下 `simSeconds` 降到 0.878 ms（**−72.4%**，接近线性的 4 倍），是典型的计算密集型。

`seq` 和 `rand` 只分别改善 **11.0%** 和 **12.6%**。原因是它们的执行时间主要由 DRAM 延迟决定，而 DRAM/总线仍跑在 1 GHz；CPU 变快只缩短了缺失之外的那部分计算。

注意 IPC 不能跨频率直接比较：4 GHz 下 `seq` 的 IPC 从 0.423 降到 0.119，`rand` 从 0.106 降到 0.030，但绝对时间反而变短。IPC 的分母是 CPU 周期，频率提高后同样的绝对访存延迟折算成更多周期，IPC 必然下降。比较性能应看 `simSeconds`。

### 5.3 L2 容量

**compute**：L2 容量和相联度完全无影响（三组 2.2%→16 MiB 都是 3.206 ms）。L2 甚至比无 L2 慢 0.8%（3.181 → 3.206 ms）：取指本来可以直达内存，经过 L2 多了一层命中/缺失判断。它的 L2 缺失率虽然 92.2%，但 L2 MPKI 只有 0.2——**缺失率单独看会误导，必须结合 MPKI 或绝对缺失数**。

**seq**（工作集 8 MiB）：
- 256 KiB 和 2 MiB 的 L2 缺失率都是 99.9%，L2 MPKI 35.6，时间 22.77 ms；
- 16 MiB 的缺失率降到 50.4%，MPKI 18.0，时间 16.13 ms（比 256 KiB 快 **29.2%**，也比无 L2 的 17.60 ms 快 8.3%）。

原因是数组先写后读：16 MiB 能装下 8 MiB 数组，第二遍读命中；小于工作集的 L2 一次也命中不了，反而在每次 L1 缺失上多加一段 L2 访问延迟——所以 256 KiB 的 L2 比**没有 L2** 还慢 29.4%。

**rand**（工作集 4 MiB）：容量效应最明显：

| L2 | 缺失率 | MPKI | simSeconds (ms) |
|---|---|---|---|
| 无 | - | - | 153.782 |
| 256 KiB | 92.8% | 97.3 | 171.809 |
| 2 MiB | 50.7% | 53.2 | 114.036 |
| 16 MiB | 7.8% | 8.2 | 55.918 |

16 MiB 能装下整个 4 MiB 链表，时间比 256 KiB 低 **67.5%**；2 MiB 只能装一半，改善 33.6%。随机访问没有空间局部性，L2 容量几乎直接等于命中率。

### 5.4 L2 相联度

256 KiB 的 8 路和 4 路在所有基准上都几乎相同：

- `seq`：22.771 vs 22.772 ms（0.004%）
- `rand`：171.809 vs 172.398 ms（0.34%）
- `compute`：完全相同

这三个负载都没有制造「多个块映射到同一组、路数不够」的冲突模式：`seq` 是流式访问，`rand` 的索引由随机置换决定、不集中，`compute` 没有数据访存。相联度只有在容量够用、但映射冲突严重时才会体现，本次没有构造这种负载。

### 5.5 负载特征

- **访存强度**：`compute` 的 L1D MPKI 0.2，`seq` 88.5，`rand` 109.5，正好覆盖「无 / 中 / 高」三档。
- **访存局部性**：`seq` 空间局部性好（每 8 次访问一次缺失），`rand` 没有局部性（几乎每次缺失），所以同样的 L2 容量对 `rand` 的收益远大于 `seq`。
- **控制规律性**：`rand` 的分支错误约 36.7 万次，是 `compute`/`seq`（约 3.3 千次）的 110 倍，主要来自 Fisher–Yates 洗牌里 `j = rand % (i+1)` 的数据相关分支。这也是 `rand` IPC 最低（0.1 左右）的原因之一。

### 5.6 敏感度汇总

以默认配置为基准，正值表示变慢：

| 参数变化 | compute | seq | rand |
|---|---|---|---|
| 发射宽度 8 → 2 | **+143%** | +0.9% | +0.3% |
| 频率 1 → 4 GHz | **−72.4%** | −11.0% | −12.6% |
| L2 256 KiB → 16 MiB | 0% | −29.2% | **−67.5%** |
| L2 8 路 → 4 路 | 0% | ~0% | +0.3% |
| 无 L2 → 256 KiB | +0.8% | +29.4% | +11.7% |

## 6. 结论

1. **负载决定敏感参数**：计算密集型只看宽度和频率；访存密集型只看容量，宽度和相联度基本无感。
2. **容量要和工作集比较**：L2 只有在能装下工作集（或大部分）时才产生收益；装不下时，加一层 L2 反而比没有更慢，因为它给每次 L1 缺失增加了延迟。
3. **缺失率不能单独用**：`compute` 的 L2 缺失率 92.2% 但 MPKI 只有 0.2，对性能没有影响。报告里用 MPKI 和绝对缺失数一起解释。
4. **相联度不是万能药**：只有当冲突缺失占主导时才有效；流式和随机访问都没有制造这种模式，8 路与 4 路几乎无差别。
5. **IPC 的口径**：频率变化时不要用 IPC 比较性能，用 `simSeconds` 或 `CPI × 指令数`。
